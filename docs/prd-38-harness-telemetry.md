## 1. Overview

PRD-37 gave the supervisor a way to choose a harness and model for a tier and to explain the choice. It also gave the ledger its first measurement of how those choices turn out: one cell per vendor × model × lane × requested tier, holding signed-off-over-finished and a median time, with `n`. That is telemetry. It is also thin: one outcome bit per attempt, no record of what kind of work the attempt was, no cost, no version of the binary that ran, no reason for a bounce, and no place where a human can look at the trend and decide anything.

This PRD makes the platform accumulate that knowledge over time and put it in front of the people who act on it, without letting it act on its own. Three parts:

1. **The attempt record.** Every delegation that finishes gets a telemetry row: what the work was (task class, lane, a size band), who ran it (vendor, model, the harness binary's version, the requested and declared tier), how it went (outcome, bounce category, turns, wall clock, tokens where the harness reports them), and how it was chosen (the resolver's first choice or a fallback). The server derives what it can from the ledger at outcome time; the supervisor posts the runtime facts it alone has, at child exit, over a narrow API-key REST route. No MCP tool, no schema property.
2. **The Harness page under Observe.** Per project: each cell's rate over time, with `n`, its version, its sampling skew, and its cost proxy, at the difficulty band the work actually had. Beside the charts, **recommended changes** — cards a rule produced from the cells, each carrying the evidence and a replay of what the resolver would have done differently. Accepting one is a human act through a surface that already exists: a commit to the matrix, a PUT to a profile or a policy. Nothing is applied by the page.
3. **The same view for an org, with a platform overlay.** An org admin sees the cells across the org's projects. On the hosted service, an org that opts in contributes anonymised cell aggregates, and every contributing org can overlay the platform average on its own charts once enough orgs contribute for the average to say nothing about any one of them.

Knowledge that reaches a chart but not an agent is half-delivered, so a recommendation that a human accepts, and a cell that crosses the sample floor, each draft a **lesson candidate** into the PRD-16 review inbox. Published, it reaches agents the way every lesson does.

### 1.1 What this is not

- Not a chooser. The resolver still resolves by PRD-37 D5 under the profile and policy; this PRD adds measured cells it already reads (with a window and a band) and nothing else to the resolution path.
- Not a job that edits the matrix. A row moves to `verified` or `failed` by a commit that names the item (PRD-37 non-goal, kept). The page drafts the commit's evidence; a person makes it.
- Not a bandit. An exploration budget — deliberately sending every Nth cheap-eligible item to the runner-up so cells fill without bias — costs real money and belongs in its own PRD. This one shows the skew so a person can choose to explore by hand.
- Not billing. Tokens are recorded when the harness reports them; cost stays a class. The page shows tokens per signed-off item as a proxy and says so.

## 2. Problem

### 2.1 One bit per attempt

`measured` knows that an attempt ended `signed_off` or not. It does not know that the item was a two-line doc fix or a schema migration, that it was the third attempt after two bounces, that the child ran 38 turns against a 40-turn budget, or that the bounce said "did not run the tests". A rate over those is a rate over noise, and it cannot be compared across cells.

### 2.2 The samples are the operator's habits

PRD-35 named the bias: frontier only sees what cheap failed. PRD-37 sharpened it: the harness the profile prefers gets the samples. A learning system fed by those samples learns the preference back and calls it a measurement. The rate must carry how the attempt came to be sampled — first choice, fallback, escalation — and the page must show the skew rather than hide it inside an average.

### 2.3 Difficulty is not recorded

A harness that is handed doc items looks better than one handed backend refactors. Until the record carries a proxy for difficulty, the rates say who got the easy work.

### 2.4 Sparsity, and versions that move

The gbagent backend/cheap cell reached `n=5` after two months on one project. Split by binary version and model name it is thinner still. `claude-fable-5-1` today; an alias tomorrow. Without the version on the record, a cell pools a harness with its own past; with it, cells rarely reach the floor. Both must be visible: current version by default, history on request.

### 2.5 Nothing feeds lessons

PRD-16 built the path from what happened to what an agent should know next time. Harness fitness — "for frontend items this quarter, cheap bounced three of four" — is exactly the kind of lesson it was built for, and nothing produces one.

### 2.6 There is no org view, and no baseline

An org running five projects has five thin sets of cells and no way to see them together. A single-project org has no way to know whether its 0.6 signed-off rate on cheap is normal. The only baseline anyone has is the matrix's committed evidence, which is one repository's history.

### 2.7 The manifest has eight tokens of headroom

The supervisor holds facts the ledger cannot derive — the binary version, turns and wall clock, tokens — and has no way to write them: every MCP tool addition is refused by the ceiling. REST is the remaining door, and it is already open to agent credentials (`POST /api/learning/run`, the `/api/sync/*` routes and the artifact writes all authenticate an API key through `get_agent_key`), so the plumbing decision here is which surface and which gate, not whether one exists.

## 3. Goals

1. Every finished delegation leaves a telemetry row with the work, the runner, the outcome and the sampling reason, derived by the server where it can and posted by the supervisor where only it knows.
2. A Harness page under Observe shows each cell's rate over time with `n`, version, skew, difficulty band and cost proxy, per project and per org.
3. Recommended changes appear as cards with evidence and a replay, and are applied only by a human through an existing surface.
4. Accepted recommendations and cells crossing the floor draft lesson candidates into the PRD-16 inbox.
5. On the hosted service, opted-in orgs contribute anonymised aggregates and see the platform average overlaid, under a k-anonymity floor.
6. The resolver's measured cells gain a recency window and a difficulty band, and remain explained.
7. No new MCP tool and no schema property.

## 4. Non-Goals

- Changing matrix status, profiles or policy automatically.
- An exploration budget or any bandit (a later PRD).
- Pooling across lanes, tiers, task classes or versions in any number a recommendation rests on. Pooling is allowed only in display, labelled as such.
- Cost accounting in currency.
- Sharing anything but cell aggregates across orgs; raw attempt rows never leave their org.
- A learned scoring model. Every number shown is a count, a rate or a median, and every recommendation names the rule that produced it.

| D1 | The unit is the ATTEMPT, one row per finished delegation | `attempt_telemetry` keyed by `delegation_id` (unique). Written once, at the outcome event, from the ledger; enriched once, at child exit, by the supervisor. Open, expired and closed-without-outcome delegations get no row: an attempt that never ran teaches nothing about the harness. |

Nothing reads it: `sampled` comes from the launch post, every rate is signed-off over finished, and no rule R1–R4 takes it as input. | D3 | The supervisor posts what only it knows: once at launch, once at exit | `POST /api/fleet/attempts`, authenticated by `X-API-Key` through the existing `get_agent_key` dependency and gated on WRITE for the project (`authz.can_write`) — the same shape and gate `POST /api/learning/run` already uses, since a read-only credential has no business adding measurements to somebody's cells. The server binds the launch row to the delegation through enrolment → agent → delegation. There is **no ordering requirement**: the route upserts, and a post that arrives before the outcome derivation creates a row holding only what it carries with `derived_at` null. **Merge rule, for every field:** a post merges non-null values in and never writes a null over a non-null; a differing non-null value wins (last write, `reported_at` advanced, `report_count` incremented) because a supervisor that read the child's result record twice is likelier right the second time, and a differing repost must be visible rather than silent. Enrolment codes are single-use (PRD-19), so exactly one process ever posts for a child. A supervisor that dies before the exit post leaves the runtime fields null and `reported_at` null — "not reported", which is the truth; on restart it re-posts for any finished child in its on-disk state (`state.py`, the record `adopt` already reads). Errors: unknown id → 404; a delegation in a project the key cannot read → 404, never 403, so a key cannot learn that an id exists; a still-open delegation → 202 and stored, with the row deleted by the same sweep that expires the delegation (D1); identical repost → 200 no-op; key without `fleet_status` scope → 403; session token → 401. Tokens come from what the harness prints: qwen's `-o json` result record, gbagent's spans, claude's `--output-format json` result; vendors that print nothing leave the fields null, and null is shown as "not reported", never as zero. The MCP manifest is untouched. |
| D4 | Rates are shown at the difficulty band the work had | Every cell is vendor × model × lane × tier × task class × size band. The page collapses task class and band by default with the pooled label visible; a recommendation never pools across them. |
| D5 | Versions are on the record and default to "current" | `binary_version` and `model` are cell keys. The page shows the current version's cells and offers history; a recommendation cites the version it is about. |
| D6 | The sample floor and the skew travel with every number, and neither touches a denominator | `n ≥ 5` (PRD-37 `MIN_SAMPLE`) for any rate to count; below it the cell is drawn grey with `n`. Every rate shows `first_choice / fallback / explicit / unknown` counts. A rate whose samples are more than 80% one sampling reason carries a "sampled by preference" badge. The badge is **visual only**: every rate on the page is signed-off over finished across every attempt in the cell, with no exclusions ever, and the rules read that same undivided rate. The badge's claim is not "this number is wrong" but "the mix of reasons this cell was sampled is lopsided, so the number is honest about what happened and is not a fair comparison against a cell chosen differently". The counts sit beside it so a reader can do their own arithmetic; the system does none on their behalf. A first-choice-only rate, if ever wanted, is a separate labelled number with its own `n` and its own floor — never a correction applied to this one. |
| D7 | Recommendations are drafts produced by named rules, and only a human applies them | Rules: **R1 promote** — an `unverified` row with ≥10 finished attempts in the window, signed-off ≥0.8 at any band, drafts matrix evidence text (item ids, dates) for a `verified` commit. **R2 demote** — a `verified` row with ≥6 finished and signed-off ≤0.25 drafts a `failed` entry naming the items. **R3 reweight** — a user's profile whose top default is beaten on signed-off by ≥0.3 at `n≥8` in the same cell drafts a defaults reorder. **R4 policy** — a `local_only` project whose local rows bounced ≥0.7 at `n≥6` drafts "consider lifting local_only for lane X", and the converse. No rule pools across task class or size band (D4), so a card fires as a claim about one band and its drafted evidence says so in those words; because the matrix's row keys are lane and role with no band, a v1 promote is at LANE granularity and the card must state on its face that it is generalising, carrying the sibling cells it did not fire on ("backend/S: 2/9") as visible context. Each card carries the cells, the rule, and a **replay** (below), and is computed once per `(rule, cell, evidence_hash)` in the nightly pass or on a read with stale rollups — never per view. Accept = copy the drafted evidence to a commit (R1/R2) or PUT the profile/policy through the PRD-37 routes (R3/R4). Accept and dismiss share one table, one card key and one hash rule: both mean "seen at this evidence", and both reopen as a new card when the evidence moves. Nothing is retracted when it does — R1/R2 applied nothing to retract, and the returning card says what changed ("the evidence behind the card you accepted on 12 Sep has changed: signed-off 0.82 → 0.55 at n=19"); R3/R4 took effect at once and the rule, being symmetric, fires the other way against the profile as it now stands. The system never edits a profile it wrote earlier. |

| D10 | The brief carries the cells for the item's lane and class, hard-capped | `get_item_details.brief.measured_for_lane`: at most **four cells** — one per tier the brief may suggest (cheap, mixed, frontier), chosen by signed-off rate, plus at most one runner-up on the tier actually suggested. Result payload only; not in the manifest is not the same as free. |
| D11 | Rollups are weekly and recomputed from raw; raw rows age out | `harness_rollups`: one row per cell per ISO week with `finished`, `signed_off`, `bounced`, `median_seconds`, `tokens_in`, `tokens_out`, `tokens_reported`, sampling counts. `median_seconds` is the median of the week's **raw attempt seconds**, computed from the rows at roll time — never a median of medians, never a median of sums; that is why raw rows are kept 400 days and why the nightly reroll recomputes rather than folds, since a rollup must be reproducible from what it summarises. Tokens are **sums over the attempts that reported**, stored beside `tokens_reported`, the count that did; no average is ever stored. The page's cost proxy is `(tokens_in + tokens_out) / signed_off among reporting attempts` — the denominator is the reporting subset, because a partial numerator over a full denominator makes a vendor that prints nothing look cheap — and it is suppressed entirely below `tokens_reported / finished < 0.8`, showing "not comparable: 3 of 11 attempts reported tokens". The page says in words that the proxy is comparable for one cell over time and only loosely across vendors, whose tokenizers differ, and that it proxies cost rather than being it. A cell with `finished=4` in a week **does** get a rollup row — a rollup is a fact about a week and the floor is a rule about a number; the floor is applied at READ, where a point under `n=5` is served `below_floor: true`, drawn grey and left unconnected to its neighbours, and no rule reads it. A week with no activity is **omitted entirely**, and the chart renders the gap as a gap: no attempts and a zero rate are different claims, and the line drawn down to zero is the false one. Rolled nightly and on read when stale. The trend chart reads rollups; the replay reads raw rows within the window. |
| D12 | The org view is the project view over the org's projects | `scope=org` aggregates cells across the org's projects for org admins (PRD-1 authz), with a per-project breakdown on expand. Same rules, same floor; a recommendation at org scope names the projects its evidence came from. |
| D13 | Platform average is hosted-only, opt-in, aggregate-only, and floored three ways | `Organization.telemetry_share` (default false). A nightly job over contributing orgs writes `platform_rollups` per cell per week with `orgs_contributing`. A cell is served only when **all three** hold: `orgs_contributing ≥ 3`, aggregate `n ≥ 20`, and no single org contributing more than 60% of that cell's attempts — the third is what answers "three orgs, one of them huge". An org counts toward `orgs_contributing` only with `n ≥ 5` of its own in the cell, so a dominant pair cannot be laundered by a third org with one attempt. The served payload carries no org id, project id, item id or reviewer, no date finer than the ISO week, rates rounded to two decimals, and `n` as a band (20–49, 50–199, 200+) — the banding being the part that matters, since a contributing org knows its own numbers exactly and could otherwise subtract itself out of a small average. Otherwise the chart says "no platform average: fewer than three orgs contribute here". Opting out removes the org going forward AND recomputes the affected `platform_rollups` from the remaining contributors, immediately on the toggle and again nightly, with any cell that falls under the floor ceasing to be served: opt-in that keeps your numbers after you leave is not opt-in. Raw rows never leave their org; only rollups do. The claim, in the doc and in the toggle's copy, is "resists casual re-identification", never "anonymous". The operator console shows the platform view whole. Self-hosted instances have no overlay and the toggle says why. |

| D16 | No manifest change | Everything travels in existing result payloads or over REST. A credential with authority reaching a second surface ungoverned is the door this repository already refuses to leave open. |

### D7 — The replay

The replay is the part that turns a card from an opinion into a claim someone can check: take the window's finished delegations for the project, rerun `Matrix.resolve` for each under the proposed change (a row flipped, a profile reordered, a policy toggled) with the profile and policy that applied, and count the resolutions that differ. The card shows "would have changed 14 of 31 cheap resolutions: 14 from claude:sonnet to gbagent:qwen3.6" and lists them. It does not claim those 14 would have gone better; it says what the change does, which is the only thing a replay can honestly say.

It is cheap, and bounded so that it stays cheap. Its input is the window's attempt rows, not the ledger, and `Matrix.resolve` is pure over (matrix, policy, profile, tier, role, lane, installed set) with no I/O — so the replay resolves each DISTINCT input once and multiplies by the rows that shared it. The distinct tuple space is tier x role x lane x the profile that applied, in practice under twenty, which makes the work O(distinct inputs) rather than O(rows). Hard caps: at most 5000 rows scanned and 200 distinct resolutions per replay; if either is hit the card is served with `replay: {truncated: true, scanned: N}` and says so on its face rather than silently sampling.

It is computed once per `(rule, cell, evidence_hash)` and stored on the card, in the nightly pass or on a read that finds the rollups stale — never per view. Invalidation is the same `evidence_hash` that governs dismissal and acceptance: when the hash changes the card is a new card and the replay is recomputed on the next read. If a recompute exceeds 3 seconds inside a read, the card is served with the previous replay flagged `stale_replay: true` alongside its `computed_at`, and the recompute is left to the nightly pass. A card never blocks the page, and a stale replay never pretends to be current.

## 6. Data model

`attempt_telemetry` (new, alembic `0111`): `id`, `delegation_id` fk unique nullable (null until the launch row binds), `enrolment_id` fk nullable, `project_id`, `item_id`, `vendor`, `model`, `binary_version` nullable, `lane`, `tier_requested`, `tier_declared`, `task_class`, `size_band`, `attempt_no`, `chosen_winner` nullable, `chosen_runner_up` nullable, `chosen_source` nullable, `sampled` (`first_choice|fallback|explicit|unknown`), `declaration_mismatch` bool default false, `outcome`, `bounce_category` nullable, `claim_to_finish_s`, `turns_used` nullable, `turn_budget` nullable, `wall_seconds` nullable, `tokens_in` nullable, `tokens_out` nullable, `exit_meaning` nullable, `derived_at` nullable, `reported_at` nullable, `report_count` default 0. Unique on `delegation_id` and on `enrolment_id`; one of the two is always present.

`harness_rollups` (new): `project_id`, `week` (ISO), cell keys (`vendor`, `model`, `binary_version`, `lane`, `tier`, `task_class`, `size_band`), `finished`, `signed_off`, `bounced`, `median_seconds`, `tokens_in`, `tokens_out`, `tokens_reported`, `first_choice`, `fallback`, `explicit`, `unknown`. Primary key on the tuple. Rows are written for weeks below the floor and omitted for weeks with no activity.

`platform_rollups` (new, hosted): the same cell keys without `project_id`, plus `orgs_contributing`. Written only from orgs with `telemetry_share = true`.

`recommendation_marks` (new): `user_id`, `scope` (`project|org`), `scope_id`, `card_key` (rule + cell + version), `evidence_hash`, `dismissed_at` nullable, `accepted_at` nullable. One table for both, because acceptance and dismissal both mean "seen at this evidence"; a card whose `evidence_hash` changes is shown again either way.

`harness_lesson_marks` (new): `project_id`, `cell_key` (the cell key MINUS `binary_version`), `first_crossed_at`, `shard_id`. Unique on `(project_id, cell_key)`. The mark is permanent: it is what makes a second crossing, a new binary version, and a rejected candidate all draft nothing.

`organizations` gains `telemetry_share` bool default false.

`memory_shards.source` gains the value `harness-telemetry`; no column change.

**Amended by the grill.** The draft recorded the resolution's winner on the seat (`Seat.chosen_by`). That cannot work: seats are minted by the PLANNER (`mint_enrolment`, PRD-19 planner-only minting) and the code reaches `spawn` already made, so the resolution happens after the seat exists and the minting call cannot carry it. `Seat.chosen_by` is dropped; the winner arrives in the supervisor's launch post (D3) and lives on the telemetry row itself.

## 7. Acceptance criteria

Each is a test. Sabotage the call, not the model.

1. A delegation that finishes produces exactly one `attempt_telemetry` row with lane, tiers, vendor, model, task class, size band, attempt number, outcome, bounce category and claim-to-finish; an open or expired delegation produces none. Sabotage: write the row at claim and the expired case fails.
2. `POST /api/fleet/attempts` with a supervisor's API key enriches the row (version, turns, wall, tokens) and is idempotent; a session token is refused; a key without `fleet_status` scope is refused; a second post does not duplicate. A launch post arriving before the outcome derivation creates the row and the derivation fills it; a post for a delegation the key cannot read returns 404, not 403.
3. Null token fields render as "not reported" on the page and in the rollup, never as zero. Sabotage: coalesce to 0 and the test fails.
4. `sampled` is `first_choice` when the declared vendor/model equals the launch post's winner, `explicit` when the spawn named an adapter, `fallback` when it equals the recorded runner-up, and `unknown` when no launch post arrived. Sabotage: drop the launch post and the row is `unknown`, never `first_choice` by default.
4a. The merge rule holds in both directions: a post carrying null for a field already set leaves it set; a post carrying a different non-null value replaces it and increments `report_count`. Sabotage: overwrite unconditionally and the null-over-value test fails.
4b. A child whose declared vendor differs from the adapter in the supervisor's exit report sets `declaration_mismatch` and the row still counts.
4c. `bounce_category` is null iff the outcome is not a bounce, and is otherwise always one of the five; an empty or unrecognised reason is `other`, shown as "unclassified". Sabotage: return null for an unmatched reason and the totality test fails.
5. Rollups: a week with three finished attempts in one cell rolls to one row with the right counts and a median taken over the RAW seconds; two cells in one week roll to two rows; rerolling from raw is idempotent; a week with four attempts is still written; a week with none is absent, and the chart renders the absence as a gap rather than a zero. Tokens are summed with `tokens_reported` beside them, and the cost proxy is suppressed below 0.8 coverage. Sabotage: store an average token count and the "not reported is not zero" test fails.
6. A rate below `n=5` is served with `below_floor: true` and the page draws it grey; a rate with more than 80% one sampling reason carries the skew badge. Sabotage: pool two cells to cross the floor and the per-cell test fails.
7. Versions: two binary versions of one harness are two cells; the page defaults to the current version and shows both on request; a recommendation names the version.
8. R1 fires on an `unverified` row with ≥10 finished and signed-off ≥0.8 and drafts evidence text naming the items; it does not fire at 9 finished, or at 0.79, or when pooled across bands would have reached the threshold but no single band does.
9. R2 fires on a `verified` row with ≥6 finished and signed-off ≤0.25; R3 on a beaten default at `n≥8`; R4 on a `local_only` project whose local rows bounced ≥0.7 at `n≥6`. Each card carries rule, cells and replay.
10. The replay reruns the PRD-37 resolver under the change and reports how many resolutions differ and to what; with no change it reports zero; it resolves each distinct input once (a window of 500 rows over 6 distinct inputs performs 6 resolutions); past the caps it is served `truncated: true`; and it is computed once per `evidence_hash`, not once per view.
11. Accepting R3 or R4 PUTs through the PRD-37 profile/policy routes and nothing else; accepting R1 or R2 copies drafted evidence and changes no server state. Dismiss hides the card for that user until its `evidence_hash` changes.
12. An accepted card and a first crossing of `n=5` each create a `MemoryShard` candidate with `source = "harness-telemetry"` in the review inbox; nothing is published; a second crossing of the same cell creates nothing, and neither does a crossing under a new `binary_version`, nor a crossing after the candidate was rejected. An unpublished candidate whose cell moves by ≥0.2 is replaced in place rather than duplicated; a published one is never rewritten.
13. `fleet_status.measured` and the brief count only the trailing 90 days and carry the band; an attempt 91 days old is absent from `n`. `brief.measured_for_lane` carries only the item's lane and class, at most four cells, and its serialised size stays under the asserted bound with twelve active vendors in the lane.
14. Org scope aggregates the org's projects for an org admin and refuses a non-admin; a project member sees only project scope.
15. Platform overlay: a cell with two contributing orgs is not served; with three and `n≥20` it is; a cell where one org holds 70% of the attempts is not served; an org with fewer than 5 of its own attempts does not count toward `orgs_contributing`; the served payload carries no org id, project id or date finer than the week, and serves `n` as a band; an org with `telemetry_share = false` contributes nothing. Toggling share off recomputes the affected cells at once and drops those that fall under the floor. Self-hosted returns `platform: null` with the reason.
16. The MCP manifest's measured token count is unchanged (`test_mcp_footprint`).
17. Operating loop, on the deployed instance: after the walk items of PRD-36/37 and ten more delegations, the Harness page shows the gbagent backend/cheap cell above the floor with its skew badge, a grey qwen-code cell, and either an R1 card for qwen-code or the reason none fired; accepting nothing, the lesson inbox holds one candidate from the floor crossing. Recorded as `note` evidence.

## 8. Phasing

**PR 1, the record.** `attempt_telemetry`, server derivation at outcome, `POST /api/fleet/attempts` with API-key auth in both shapes, the supervisor's launch post and exit report, `sampled` from the launch post, the 90-day window and band on `measured`. Criteria 1–5 (with 4a–4c), 13, 16.

**Turns and tokens are not in PR 1.** They live in each vendor's own result record, and this repository has measured that record's shape for no vendor. A parser written from memory would put invented numbers into the one table whose whole purpose is to be checkable, so the columns ship and stay null — which the page renders as "not reported" — and a follow-up fills them per vendor, one measured shape at a time. `turn_budget` is posted, because the supervisor set it.

**PR 2, the page.** Rollups, the Harness page under Observe for a project: trend per cell, floor, skew, versions, cost proxy; `doctor` prints the same cells. Criteria 6, 7.

**PR 3, recommendations and lessons.** Rules R1–R4, the replay, accept and dismiss, lesson candidates. Criteria 8–12.

**PR 4, org and platform.** Org scope, `telemetry_share`, the platform rollup job, the overlay and its floor, the operator console view. Criteria 14, 15. Then criterion 17.

## 9. Risks and open questions

### Risks

- **Reviewer variance.** Signed-off depends on who reviewed. A strict reviewer on one lane depresses every harness there equally, which the per-lane cells absorb, but a reviewer who favours one vendor's style is a bias no cell can see. Mitigation: the org view shows rates per reviewer on expand, labelled as a diagnostic, not a rule input.
- **Gaming by declaration.** Cells attribute by what the child declared (GRPH-732). A child that declares a vendor it is not is a lying child; the supervisor's exit report carries the adapter it launched, and a mismatch is flagged on the row, not silently trusted either way.
- **Thin cells forever on small instances.** A one-person self-hosted box may never cross the floor on anything but its favourite. The page must be honest about that rather than decorative; the platform overlay is the hosted answer, and there is no self-hosted one.
- **Bands the matrix cannot express.** Rules fire per size band, but a matrix row's keys are lane and role with no band, so "verified for backend/L, not for backend/S" is not expressible in the matrix today. v1 promotes at lane granularity, and the card must say on its face that it is generalising, with the sibling cells it did not fire on shown beside it. Band-scoped matrix rows are a follow-up, not something this PRD quietly pretends to have.
- **Rules that are wrong.** R1–R4 are first guesses at thresholds. They are drafts to a human, so a wrong rule costs attention, not a bad spawn; thresholds are constants in one module and the page shows them.

### Open questions

1. **Closed by the grill: the supervisor posts.** The child is the thing being measured, which makes it the wrong witness — a child that burns its turn budget, exits non-zero, or dies never writes a last `update_item`, and those are exactly the attempts telemetry must not lose. The supervisor observes exit for every child, including the ones that fail. Neither side is trusted blindly: the supervisor reports the adapter it launched, the ledger holds what the child declared, and a mismatch is flagged (`declaration_mismatch`) rather than believed or dropped.
2. **Closed by the grill: a constant 90 days.** A per-profile window makes every explanation carry a parameter, and the explanation is the feature. `window_days` stays a REST read parameter for a human looking at history.
3. Does the platform overlay need a per-cell opt-out beyond the org toggle (e.g., an org willing to share backend cells but not frontend)? D13 says no for v1. Still open.
4. Should an org admin be able to accept an R3 card on a member's behalf? D7 says a profile is its owner's; the card at org scope is informational. Still open.

## 11. Amendments

**v1.1, while building PR 1.** Three claims in v1.0 were wrong or imprecise about code that already exists, and the doc is corrected rather than left to be discovered again:

1. **`POST /api/fleet/attempts` is not the first API-key REST route.** `POST /api/learning/run`, the `/api/sync/*` routes and the artifact writes already authenticate an API key through `get_agent_key`. §2.7 and D3 said the REST surface authenticates humans only; it does not, and the correction makes D3 cheaper — an existing dependency and an existing gate, not a new authentication path. What IS new is that the supervisor now reaches two surfaces on one credential, which D16 answers with a pinned path allowlist on the client.
2. **"Scoped to keys that carry `fleet_status`" named a tool, not a scope.** Key scopes are `read`/`write`/`sync`/`gate`, and every key can call `fleet_status`. The gate is WRITE on the project.
3. **The exit post needs the seat as an address.** The supervisor holds the enrolment's row id from the roster and not the delegation id, so `enrolment_id` joins `delegation_id` and `enrolment_code` as an address. This is the same finding as the v1.0 grill's — the planner mints the seat before the resolution exists — arriving a second time, from the other end.

None of these change what the record holds or what the page will show.
